# 調べ方

**測る前に「その測定器はこの故障を見られるか」を確かめる。** ここに挙げるのは、このリポジトリで
実際に測定器の側が壊れていた事例である。

実行するコマンドそのものは [commands.md](commands.md)、どこまで走らせるかは [../agents/verification.md](../agents/verification.md)、
E2E の3本が何を見ているかは [../quality/test-strategy.md](../quality/test-strategy.md) にある。

## 直したのに変わらない

1. **見ているのは `out/` か、dev サーバか。** E2E は `out/` を配る。`npm run build` をしていなければ古い `out/` を測っている
2. **WSL の `/mnt/c` 上では dev サーバが古いバンドルを配り続ける。** ソースを戻しても症状が変わらないなら、まず配信物を疑う。dev サーバを再起動する
3. **`sessionStorage` / `localStorage` に古い値が残っていないか。** 村の位置・訪問記録・テーマは保存される。新しいタブやシークレットウィンドウでの確認は「初回訪問の確認」であって「移行の確認」ではない

## 検査は通るのに画面がおかしい

- **CSS の特異度負け**。`.parent button` のような既存規則が新しいクラスに勝っていることがある。症状(「折り返しが消えた」)ではなく `getComputedStyle` の値そのものを単言する
- **ビルド後の CSS を見る。** ベンダープレフィックスを手で書くと、ビルド側の自動付与と衝突して標準宣言が成果物から消えることがある。プレフィックスは手書きしない
- **ヘッドレス特有の描画ずれ**。DOM の実測(`getComputedStyle` / `getBoundingClientRect`)が正常なのにスクリーンショットだけ変なら、アプリではなく描画経路を疑う。実機か headed で撮り直してから判断する

## 入力が落ちる・カクつく

村で「たまにキーが効かない」類は主スレッドの停止を疑う。`PerformanceObserver('longtask')` と rAF の間隔で
停止の時刻を取り、その時刻のトレースで **Paint の中に何が何回あるか**を数える。
過去の実例と対策は [../quality/performance.md](../quality/performance.md)。

## 実機でだけ起きる

1. エミュレータのタッチは、ブラウザがジェスチャを先取りする経路(`pointercancel`)を再現しない。**ハネスが PASS でも実機 FAIL は起こる**
2. 同じコードベースに**同じ配置パターンで実機実績のある前例**が無いか先に探す。あればそれに合わせる
3. 症状が出た時点の配信バンドルにその要素が存在したかを、コミット履歴で確かめる(古いバンドルのキャッシュを先に潰す)
4. 検証できない方向転換を推測で提案しない。確かめられる案が無いなら、実機確認が前提であることを明示する

## 検査スクリプトを疑う順番

自作の検査は本体コードより新しく、レビューされておらず、実行回数も少ない。**FAIL が出たらまず判定式を疑う。**
浮動小数の比較・境界の等号・`'10px'` と `10` の比較・待ち時間不足が典型。
逆に **PASS のほうが危険**で、対象 URL が引数を無視していないか、検査対象の件数が意図と同じかを数える。
