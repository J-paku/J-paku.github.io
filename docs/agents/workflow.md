# 作業の進め方

## 着手前

1. [../../AGENTS.md](../../AGENTS.md) の不変ルールと routing 表を読む
2. 作業を分類し、**routed された文書だけ**を読む。`docs/` を再帰的に読まない
3. 触る範囲に `AGENTS.md` があれば先に読む(`content/` / `src/lib/pixel/` / `src/components/VillagePage/`)
4. **検証手段を先に決める。** 段階と検証を対にして書き出す。「動くようにする」は検証手段ではない

```
1. {やること} → verify: {何を見れば済んだと分かるか}
2. {やること} → verify: {…}
```

verify が埋まらない段階は、まだ定義が足りていない。

## 実装

5. **同種の既存実装を1つ開く。** 新しい書き方を持ち込む前に、既にある解き方で足りないかを確かめる
6. 最小の一貫した変更に留める。ついでの整形・リファクタ・抽象化を混ぜない
7. UI 要素の**位置**を決めるなら、先に現ビルドを撮って「その場所に今何が描かれているか」を見る。重なりはレンダー結果にしか無い

## 検証

8. 狭いものから走らせる。範囲は [verification.md](verification.md)
9. 新しく書いた検査は採用の前に一度わざと落とす(→ [../quality/test-strategy.md](../quality/test-strategy.md))
10. FAIL のとき・PASS のときに何を疑うかは [../development/debugging.md](../development/debugging.md)

## 報告

11. 「完了」「動作変更なし」「純粋な移動」と書くなら、**実行結果か diff の対照を添える**。予測は根拠ではない
12. 走らせられなかった検証があれば、何を確かめていないかを明示する
13. 失敗したテスト・型エラー・lint エラーを黙って飛ばさない
14. **ローカルの PASS だけで完了と言わない。** 配信に関わる変更は配信版でも同じ確認を繰り返す
15. Source of Truth が変わったときだけ文書を直す。判断基準は [../README.md](../README.md)

## やらないこと

- コミットの扱いは [../../AGENTS.md](../../AGENTS.md) の「コミット」に従う
- 破壊的な git 操作(`push --force` / `reset --hard` / 公開済みコミットの改変)を近道に使わない
- 元から死んでいたコードを「ついでに」消さない。報告に書くだけにする
