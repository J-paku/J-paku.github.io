## commit の直前

そこまでに触った範囲に関係なく、**`npm run verify` を1回通す**。
中身は docs:check → lint → format:check → test:coverage → test:boundary → test:integration → build の直列で、前段が落ちたら後段は走らない(正本は `package.json` の `scripts`)。

これに、上の表で変えた範囲が指すものだけを足す。

- E2E は表が指す spec だけ(`npx playwright test tests/journey.spec.ts` のように)
- `npm run test:mutation` は、純粋モジュール(変異テストの対象。`scripts/gate-targets.mjs` の `MUTATION_TARGETS`)かそのテストを変えたときだけ。
  既定は前回の結果を引き継ぎ、変わった変異体だけを走らせる。git のフックで毎回走らせることはしない。
  テストが import する補助のファイル(`*.test-helper.ts`・`*.fixture.ts`)や、テストが間に挟んで import するファイル・content だけを変えたときも、既定の実行で測り直す
  (入口の `scripts/run-mutation.mjs` が、テストから import をたどって届くファイルが変わったテストの前回落とした変異体を取り除いてから走らせる。[../decisions/0025-remeasure-kills-on-test-deps.md](../decisions/0025-remeasure-kills-on-test-deps.md))。
  ただし、テストが `fs` で読むファイル・src と content の外のファイル・式で組んだ `import()` の先だけを変えたときは、既定の実行では測り直さないので `npm run test:mutation -- --force` で走らせる(指紋に入らないものと、今ある `fs` の読み出しの一覧は 0025 の Consequences)。
  変異体を全部走らせるのは週1回、手で `npm run test:mutation -- --force`([../decisions/0013-incremental-mutation-on-push.md](../decisions/0013-incremental-mutation-on-push.md))。
  依存・設定を変えたときも、その場では全部を走らせず、この週1回で測り直す(今は手で走らせ、定期的に走らせる形は後の課題。[../decisions/0023-inherit-latest-mutation-result.md](../decisions/0023-inherit-latest-mutation-result.md))

`npm run typecheck` を入れないのは、`npm run build` の `next build` が同じ `tsconfig.json` で型を検査するから。
2026-10-11 に src のソース・単体テスト(`src/lib/village/is-moving.test.ts`)・E2E の spec(当時の flight の spec。2026-10-15 に統合テストへ移して消した)へそれぞれわざと型の誤りを入れ、`tsc --noEmit` と `next build` が3つとも同じ誤り(TS2322)で落ちるのを確かめた。
`typecheck` は反復中の速い確認として上の表に残す。

表が指していないかぎり、**E2E の全体・変異テスト・axe・Lighthouse CI・日本語改行検査は手元で走らせない。**
CI(`.github/workflows/deploy.yml`)が `main` への push のたびにこれらを走らせ、`deploy` ジョブは `needs: build` なので、どれか1つでも落ちれば公開されない。
手元で同じものを回すのは、同じ門を2回通るだけである。そのかわり**完了は CI が通ったことで言う**(ローカルの PASS だけで完了と言わない)。

例外は、表の「依存の版」と「`.github/workflows/`」の行。そのときは門そのもの(道具の版・CI の手順)が変わるので、表のとおり push の前に [../operations/deployment.md](../operations/deployment.md) の「ローカルで CI を再現する」のコマンドを全部通す(`main` に入る前に CI で試す場は無い。[../decisions/0020-direct-push-to-main.md](../decisions/0020-direct-push-to-main.md))。

配信に関わる変更なら、さらに配信版で受け入れ確認を繰り返す([../operations/deployment.md](../operations/deployment.md))。

## 反復中の走らせ方

E2E の全体は数分かかる(2026-10-11 の手元の実測で約3分44秒)。修理のたびに全体を回さない。

- 反復中: 落ちた spec と新しく書いた spec だけ(`npx playwright test tests/journey.spec.ts -g '<名前>'`)
- 統合テスト(`npm run test:integration`)はビルド無しで走るが、全体は約51秒かかる(2026-10-18 の手元の実測、87ファイル・314件、`--coverage` 無し)。反復中は触ったコンテナの統合テストだけを狭めて走らせ(ファイル1つを `-t` で絞るなら `npm run test:integration -- src/components/VillagePage/__tests__/fishing.integration.test.tsx -t '<名前>'`、コンテナ1つの `__tests__` なら `npm run test:integration -- src/components/Story/components/StoryBody/__tests__/`)、全体は commit の直前に1回(`npm run verify` に含まれる。[../quality/test-strategy.md](../quality/test-strategy.md) の「走らせる範囲」)
- E2E の全体は手元では回さず、push で CI が回す。CI で落ちた spec が出たら、その spec だけを手元で狭く直してから push し直す
- CI も E2E を再試行しない(`playwright.config.ts` の `retries` は 0)。1 回だけ落ちて次は通る揺れも、再実行で流さず原因を直す

## 走らせたと言ってよい条件

- **実際に実行した出力を見たときだけ**「通った」と書く
- 実行できなかった検証は、何を確かめていないかを明示する
- 他のエージェントやワーカーの「直した」という報告は、**ファイルか diff を自分で見るまで根拠にならない**
